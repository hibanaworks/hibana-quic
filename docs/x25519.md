# Bounded X25519 integration

The provider offers fresh X25519 and P-256 shares and prefers an available
X25519 share on the server. ECDSA P-256 certificate authentication remains a
separate algorithm/profile choice. Normal ServerHello and strict selected-group
HRR parsing support both groups. A second ClientHello still contains exactly one
requested share; the previously captured Neqo HRR+extra-GREASE message remains
rejected. Accepting Neqo's ordinary X25519 first share avoids that path; it does
not make the historical malformed message conformant.

The implementation uses official `x25519-dalek = 2.0.1` with default features off,
`static_secrets` and `zeroize`, backed by `curve25519-dalek = 4.1.3`. Registry
checksums are in Cargo.lock. The 2.x release is intentionally pinned to this
compatible fixed-storage backend; it is not represented as the latest version.
No curve arithmetic is implemented locally. The wrapper does not expose cloning,
serialization or raw-secret construction: it requires fresh fallible injected
CryptoRng bytes and consumes the owner on agreement. The upstream static-secret
constructor is used to handle entropy failure explicitly; it does not authorize
reusing a key. Secret and shared-secret owners zeroize on drop, and unused group
secrets are dropped after selection.

Length checks precede agreement. The upstream contributory check rejects an
all-zero shared secret before TLS keys are installed. RFC7748 public-input
high-bit handling is preserved. See the
[RFC7748 algorithm and vectors](https://www.rfc-editor.org/rfc/rfc7748.html#section-6.1)
and [official implementation](https://github.com/dalek-cryptography/curve25519-dalek/tree/4ac84dd0668b1d2e51654fcdffe4ae6a687bef00/x25519-dalek).

Evidence includes the RFC agreement vector, low-order/length/high-bit/entropy
cases, dual-share/HRR framing and truncation tests, both-role real Rustls
handshakes, measured bounded success/failure paths, and direct default-group Neqo
transfers reporting group29. `BoundedTls::server_p256` retains explicit P-256-only
policy so genuine HRR tests remain exercised rather than silently disappearing.
The target no_std build passes; actual board timing/stack/high-water measurements
remain outstanding. Neither dependency choice nor vectors establish a complete
side-channel proof of the TLS/QUIC pipeline.
