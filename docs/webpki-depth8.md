## Why this is sufficient at the validator layer

`MAX_SUB_CA_COUNT` sizes both `PartialPath.intermediates` and `Intermediates::Owned.certs`. `PartialPath::push` rejects the ninth intermediate after this change. The existing recursion still visits every CA, `check_issuer_independent_properties` still enforces pathLen and validity, `check_signed_chain` verifies every signature, and `check_signed_chain_name_constraints` iterates every CA's constraints. The supplementary KeyUsage loop sees all eight actual intermediates in the verified path.

Keep these upstream budgets unchanged:
- Signature checks: 100
- Recursive path-building calls: 200000
- Name-constraint comparisons: 250000

The simple positive chain uses eight path pushes and nine signatures. The extension raises bounded maximum depth, not any work-budget counter or trust condition.

## Exact runner fixture

Runner repository is clean at `740c05a10b61d65e8abd3ad38d60898004d335d9`. The fixture was generated by its unmodified `certs.sh` and `cert_config.txt`, using `bash certs.sh /tmp/hibana-webpki-depth-prototype/fixtures/runner9 9` from the runner directory.

The wire chain contains leaf plus eight intermediates; the separate root is the trust anchor. This generated instance has DER sizes `[5516,514,515,513,514,514,514,527,538]`, totaling 9665 bytes. TLS Certificate encoding needs 9718 bytes (8-byte header/context/list overhead plus five bytes per certificate). Certificate signatures and random SAN strings make individual lengths vary slightly on regeneration.

The exact root authenticates `server`, `server4`, `server6` and `server46`; unrelated hostname and unrelated CA reject. Existing webpki depth6 rejects the exact chain with MaximumPathDepthExceeded. Depth8 validates it.

## Integrated changes

1. Vendored pinned dependency and explicit patch/provenance documentation (vendor/webpki-provenance.json)
2. tls_certificate.rs: MAX_INTERMEDIATES 6→8; update fixed boundary test `[CertificateDer;7]` to `[CertificateDer;MAX_INTERMEDIATES+1]`
3. tls_wire.rs: MAX_CERTIFICATES 7→9; update boundary test currently treating eight certificates as too many to use MAX_CERTIFICATES+1
4. bounded_tls.rs derives MAX_CHAIN from MAX_INTERMEDIATES+1 already; its persistent DerRange array and temporary CertificateDer array expand automatically from seven to nine
5. Existing per-certificate limit 8192 and total-chain limit 32768 suffice for this exact fixture and can stay unchanged
6. Caller-supplied rx_message, tx_flight and peer_certificates buffers must each fit the enlarged Certificate/full flight; 16384-byte profile is sufficient for the observed fixture. Handshake CRYPTO reassembly must fit the whole flight too. The current bounded adapter uses 8192-byte arrays and cannot pass merely by raising chain counts

If all three TLS buffers and all three encryption-level CRYPTO buffers are uniformly raised 8192→16384, plus their bitmaps, persistent caller-owned storage rises 52224 bytes (51 KiB). A caller can provision only the Handshake CRYPTO buffer at16 KiB rather than all three, reducing this delta to 33792 bytes (33 KiB), provided its current storage API keeps levels separate. No allocator is introduced.

## Layout and stack cost

Measured using Rust1.95.0 for thumbv6m-none-eabi without allocation features:
- Cert and Option<Cert>:120 bytes
- Owned VerifiedPath:736→976 bytes, +240
- PartialPath's certificate array:720→960 bytes, +240, plus unchanged pointer/count
- BoundedTls persistent DerRange storage: +16 bytes (two8-byte ranges)
- Temporary CertificateDer array: +16 bytes (two8-byte views)

Stack cost exceeds the two extra entries because the recursive builder has local path-related values. The isolated release opt-level3 diagnostic emitted `.stack_sizes` with `RUSTC_BOOTSTRAP=1 cargo rustc --lib --target thumbv6m-none-eabi --release -- --emit=obj -Z emit-stack-sizes`. Bootstrap was used only to emit diagnostics; it did not change production source or install a compiler.

Observed frames:
- build_chain_inner:1168→1416 bytes
- verify_server:2680→3400 bytes
- verify_certificate_verify:224 bytes unchanged

At maximum accepted depth, initial end entity plus6 or8 intermediate frames gives the subtotal `2680 + 7*1168 = 10856` versus `3400 + 9*1416 = 16144`, delta 5288 bytes. This is a compiler/profile-specific local-frame subtotal, not a proven full firmware stack peak. It excludes signature and parser callees, provider callers, platform startup and interrupt stacks. Final linked LTO/profile analysis and target stack high-water measurement remain required before declaring a Pico memory budget acceptable. Stack reports are in thumb-stack.json and ../hibana-webpki-depth-baseline/thumb-stack.json.
