# Bounded certificate-validation profile

`src/tls_certificate.rs` validates borrowed server chains using ECDSA P-256/SHA256,
RSA-PSS-rsae/SHA256 and certificate-only RSA-PKCS1-v1_5/SHA256. RSA permits exact
2048/3072/4096-bit moduli and odd public exponents from 3 through 2^32−1. This is a
bounded verification profile; RSA signing, PSS-restricted SPKI, other hashes and
full TLS release conformance are not claimed.

## API and ownership

1. Provision trusted root DER through the caller's trust policy, then call
   `trust_anchor_from_der(&CertificateDer)`. Parsing a root does not establish
   trust or verify its self-signature
2. Construct `ServerVerifier::new(&anchors, UnixTime, Limits)`. The caller supplies
   trusted time and owns every root/peer DER byte; there is no clock/name bypass
3. Call `verify_server(&leaf, &intermediates, &ServerName)` for chain signatures,
   validity, constraints, usage and hostname. Its borrowed
   `ValidatedServerCertificate` is not yet an authenticated TLS connection
4. Call `verify_certificate_verify(scheme, &transcript_hash, signature)` before
   adding CertificateVerify to the transcript. It permits 0x0403 ECDSA-P256 or
   0x0804 RSA-PSS-rsae/SHA256. PKCS1 scheme 0x0401 and restricted-PSS 0x0809 reject
5. The surrounding provider must verify Finished, negotiation, ALPN, transport
   parameters and message order. QUIC handshake confirmation is separate

The target graph uses pinned no-default-feature webpki 0.103.15, pki-types 1.15.1,
p256 0.13.2, der 0.7.10, pkcs1 0.7.5, crypto-bigint 0.5.5, SHA256 and the six unchanged
RustCrypto RSA 0.9.10 verification helpers. There is no ring/aws-lc/allocator in
this component. The separately allocating rustls reference graph can enable
allocating webpki error diagnostics and is not the embedded feature closure.

## Exact algorithm and usage checks

webpki compares signature and public-key AlgorithmIdentifier bytes against the
registered adapters before invoking signature verification. `RsaPssSha256` uses
official pki-types `RSA_ENCRYPTION` and `RSA_PSS_SHA256`: rsaEncryption with NULL
key parameters, SHA256, MGF1-SHA256, salt32, and the default trailer. PSS-restricted
SPKI cannot match the rsae verifier. Unsupported parameters are not normalized
into a supported algorithm.

`RsaPkcs1Sha256` accepts the two exact certificate signature identifiers required
by RFC4055 section 5: sha256WithRSAEncryption with NULL, or absent parameters. The
latter reuses the identifier bytes from pinned webpki. This exception does not
relax the signature's inner DigestInfo: the upstream helper requires canonical
SHA256 DigestInfo including NULL. PKCS1 is never a TLS1.3 CertificateVerify mode.

webpki checks chain signatures, validity, basic/path/name constraints, server EKU
and DNS/IP name matching. A borrowed `der` extension reader supplements webpki's
KeyUsage handling: digitalSignature for a leaf and keyCertSign for selected-path
CAs when that extension exists. There is no permissive failure fallback.

Default caps are 8 KiB per peer certificate, 32 KiB total peer chain, eight
intermediates and sixteen roots. Hard caps are 65,535 bytes per certificate,
eight intermediates, 32 roots and 64 supplementally parsed extensions. The reviewed
webpki depth adjustment retains its original signature/path/name-comparison work
budgets. These limits are not a target latency or stack qualification.

## Evidence

Existing P256 tests use public rcgen/ring fixtures and cover chain/name/time,
KeyUsage/EKU, malformed/truncated DER and CertificateVerify context/signatures.

`adapters/host/tests/rsa_certificates.rs` adds six groups with 32 public fixtures
independently generated by Python cryptography 50.0.0 and cross-checked using
OpenSSL 3.5.7. Every bounded call is measured, including anchor import and failures:

- RSA 2048/3072/4096 chains signed with both PKCS1 and PSS, followed by real PSS CV
- Wrong root/name/time, leaf/CA KeyUsage, EKU and modified/truncated certificates
- Independently valid certificates with unsupported PSS salt/hash/MGF or PKCS1 hash
- Valid PKCS1 CV, wrong PSS salt/MGF, wrong transcript, corrupted/short/long CV rejection
- Mixed ECDSA root→RSA 3072 CA→ECDSA leaf, name constraints and pathLen enforcement
- Valid absent-PKCS1 signature parameters; valid signed restricted-PSS and
  missing-NULL RSA SPKI chains whose rsae CertificateVerify must fail

All six groups and the 1,224 RSA signature cases pass at zero measured allocations
in the isolated actual-core harness. Strict Clippy and thumbv6m compilation pass.
The public corpus, generator and hashes are under `tests/vectors/certificates/rsa`;
private fixture keys are never committed. Logs and independent OpenSSL checks are
in `artifacts/rsa-certificate-integration`. The independent primitive review is
`artifacts/rsa-independent-review/REVIEW.md`.

## Target cost and remaining work

A measured non-inlining change isolates fixed-width RSA workspaces without
changing arithmetic or extracted helpers. Visible wrapper/common/width/bigint
call-path subtotals are 18,040/26,504/34,944 bytes for 2048/3072/4096. External callees,
webpki/TLS callers, interrupt frames and final-link effects remain unmeasured.
The 4096 subtotal is 288 bytes larger than the earlier shared-dispatch baseline;
this is not a claim of a smaller maximum stack. See
`artifacts/rsa-stack-isolation/manifest.json` and `tls-rsa-feasibility.md`.

`reference-tls/tests/rsa_tls.rs` now proves bounded-client negotiation and real
RSA 2048/3072/4096 authentication against the independent rustls server, with
bidirectional 1-RTT packet keys and zero allocations in measured bounded calls.
A cryptographically valid QUIC-protected flight containing a corrupted RSA
CertificateVerify fails before application keys. OpenSSL generates ephemeral
private fixture keys in memory outside the counter; no private key is committed.
This adds verification, not RSA server credential signing.
Revocation/OCSP/CRL policy, client certificates, dynamic trust-store management,
other algorithm profiles, a full audit/formal proof and hardware memory/latency
qualification remain separate work. Existing full-handshake and resumption
coverage is described in [bounded-tls.md](bounded-tls.md).

Standards: [TLS CertificateVerify](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.4.3),
[RFC4055 RSA parameters](https://www.rfc-editor.org/rfc/rfc4055.html),
[RFC8017 signature encoding](https://www.rfc-editor.org/rfc/rfc8017.html).
